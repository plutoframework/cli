# Pluto CLI (initial prototype)

A working Cobra generator for small Go/Chi APIs. The application uses provisional
app-local primitives, **not an imaginary published Pluto framework**. The module is
`github.com/plutoframework/cli`. Go 1.25.5+ and Git are required.
The executable is named `pluto`; install the release with
`go install github.com/plutoframework/cli/cmd/pluto@v0.2.0`.

```sh
git clone https://github.com/plutoframework/cli.git pluto-cli
cd pluto-cli
go build -o ./bin/pluto ./cmd/pluto
export PATH="$PWD/bin:$PATH"
pluto --help
pluto version
# Or: go install ./cmd/pluto (installs into GOBIN / GOPATH/bin)

pluto init /absolute/path/my-api --module example.com/my-api \
  --env-prefix MY_API_
cd /absolute/path/my-api
pluto add endpoint widgets Create --method POST --path /api/widgets \
  --name 'Create widget' --description 'Create an authorized widget.' \
  --permission widgets.write --feature widgets-create --feature-client-visible
pluto add endpoint widgets Get --method GET --path '/api/widgets/{id}' \
  --name 'Read widget' --description 'Read a widget in the verified scope.'
pluto add endpoint reports List --method GET --path /api/reports \
  --name 'List reports' --description 'List authorized reports.'
pluto fmt
pluto vet
go run ./cmd/api
# curl http://127.0.0.1:8080/healthz
```

`init [directory]` defaults to cwd. `--name`, `--module`, `--env-prefix`,
`--multi-tenant` and optional `--hook` configure the scaffold. Docker, mise and
fnox files are generated by default. Omit presets independently with `--no-docker`,
`--no-mise` and `--no-fnox`, for example:

```sh
pluto init minimal-api --no-docker --no-mise --no-fnox
```

`--no-mise` leaves fnox usable directly via `fnox exec -- go run ./cmd/api`.
`--no-fnox` leaves mise's run task as plain Go. Existing manifests retain their
saved choices; endpoint additions do not enable previously omitted presets.
Core lint/config/SQL files are always generated. Hooks remain opt-in.
Tenancy defaults single; multi requires a verified
tenant principal. `--public` is an explicit single-tenancy opt-in; scoped public
business routes are refused in this version. `--dry-run` preflights without writes
on init/add. Every error exits 1; success/help/version exit 0. The Cobra tree accepts
injected streams, directory and execution context for tests; no process chdir.

Protected endpoints fail closed until a real authenticator is injected in cmd/api.
No published demo token, fake identity provider or trusted arbitrary tenant header.
The server runs, and public liveness works; generated business operations return
501 after authentication/permissions/flags pass. The generated tests prove that
incomplete operations never claim success. Resource authorization remains authored
business logic, separate from route permissions and feature gates.

Authorization uses the published `github.com/plutoframework/pluto-rbac` module,
pinned to `v0.1.0` in the CLI and generated apps.
The CLI validates permission IDs with that library, including `resource:action`
IDs. No local `replace` or sibling checkout is required.

Generated `internal/access/permissions_gen.go` holds deduplicated capability
declarations and endpoint permission constants. Authored `internal/access/roles.go`
starts empty: declaring a capability never grants it automatically. Define named
roles, grants and optional inheritance there; customize display metadata through
authored `access.Permissions()`. Startup compiles one policy and injects it through
the router and `app.Dependencies.Policy` into each operation constructor.
Authenticators return trusted `Principal.Roles` for the verified actor/tenant.
Both route and direct operation permission checks use that same policy; unknown
roles invalidate the complete assignment, and a nil policy grants nothing.
Ownership, tenant-scoped SQL and revocation consistency remain application policy.

The templates change authored principal, composition and operation signatures.
Existing generated apps need an explicit RBAC migration (or a fresh scaffold);
`add endpoint` does not overwrite authored files to perform that migration.
The separate purchasing example is already integrated with this package.

The generated README and AGENTS explain config, injection, models, strict bounded
JSON, diagnostics, tests, Docker, secrets and the ownership boundary. Defaults then
explicit uppercase environment overrides are loaded/validated once. `.env` is never
automatically loaded. Explicit false survives feature override resolution. Flags
start false and private flags never appear in authenticated `/api/features`.
No secrets or runtime settings belong in pluto.toml.

New apps include a global stdlib security-header middleware in authored
`internal/transport/security.go`, inspired by
[Fiber Helmet](https://docs.gofiber.io/next/middleware/helmet/). Defaults include
nosniff, frame denial, no-referrer, a restrictive JSON-API CSP, disabled camera/
microphone/geolocation, cross-origin isolation/resource policies and legacy
browser hardening. The policy also covers errors and recovered panics. Generated
docs explain customization for HTML/docs, separate CORS configuration and HSTS
at the HTTPS terminator. No Fiber dependency or automatic HSTS/preload is added.
Rebuild the CLI before generating an app; existing authored app middleware is
preserved and must be updated deliberately.

`pluto.toml` schema **6** records project/capability/database/development settings,
endpoint definitions and typed job registrations. Unknown fields, incompatible
versions, conflicting routes, job kinds and feature environment aliases fail
validation. Older schemas require a deliberate manual migration.
Metadata is authored once in TOML; generated paths/feature definitions/registries
serve it at runtime. `pluto openapi` derives an artifact from those paths and actual
Go wire models; `--check` verifies freshness. Endpoint addition automatically regenerates it.
No business validations, resource policies or recursive model support are inferred.

`*_gen.go` is wholly CLI-owned and checked semantically before regeneration.
Per-endpoint handler, operation, model and test files are created once, never
rewritten. Config, transport and the composition root are authored too. Grouped
registries reference explicit constructors; there is no magic init, raw replacement
of custom code, service locator or global mutable app state. Repeated additions in
the same/different groups work; conflicts leave authored files unchanged. One group
or artifact approaching 1,000 lines needs deliberate splitting; the generator does
not compact code to evade the limit. This version has no metadata-edit/regenerate
command or endpoint deletion workflow: restore metadata/contracts before adding,
or deliberately take ownership and migrate the generator boundary.

Init refuses any planned file conflict, even an existing README, and symlink
components/traversal. Repeated init refuses without changing the project. All known
file/hook conflicts are checked before writes; ordinary write failures roll back
owned files (empty directories may remain). A concurrent writer, process crash,
Git failure or post-write Go/OpenAPI/tool download failure is outside that file
transaction; errors explicitly report post-write failures. Init/add need the Go
module cache or network to compile OpenAPI. No offline promise is made.

Git init runs only outside an existing worktree and disables template hooks. No
ancestor configuration or hooks are changed implicitly. Hooks are **opt-in**:
`pluto init --hook` or `pluto hook install`. Existing hooks are never replaced or
run; compose your own dispatcher if needed. Effective core.hooksPath and linked
worktrees are resolved through Git. Nested projects refuse hook installation;
inherited external hook paths for new repos are refused. No global Git config is
written. An installed hook resolves its root and executes `pluto vet --staged`.

Staged policy is deliberately conservative: no unstaged, untracked **or ignored**
project extras, no conflicts, symlinks or submodules; every indexed regular file's
raw blob hash must match its working file. This also detects assume-unchanged and
skip-worktree hiding, and refuses clean/smudge/line-ending transformations that
would differ. Only then is the working tree vetted. Stage everything before
committing; ignored local .env/bin files must live outside the project for hook
use. No stash/index mutation or staged-snapshot claim. CI should use `pluto vet`.
External toolchain/environment configuration is outside this staged policy.

Install **golangci-lint 2.15.0** on PATH from its official releases, or use
`mise exec golangci-lint@2.15.0 -- pluto fmt` / `... -- pluto vet` after trusting
the generated mise config. Missing/wrong tools fail with guidance. The generated
.golangci.yml is app-configurable: golines 80 (not a blanket line-length rejection),
gofumpt, gci, wsl_v5, govet, ineffassign, staticcheck and unused. Fmt runs formatters,
whitespace fixes, then formatters again. Vet never rewrites source: it checks
manifest/generated contracts, transitive architecture imports, the hard 1,000-line
ceiling, formatter diff, pinned static analysis, Go vet, tests and OpenAPI freshness.
AST/import rules enforce dependencies; they cannot prove handlers lack all business
logic or inspect arbitrary third-party package internals.

Developer presets are generated by default and can each be omitted. Mise pins
Go 1.25.5, lint 2.15.0, sqlc
1.31.1 and optionally fnox 1.43.0. Fnox scopes env injection with `fnox exec --` and
ships only a nonsecret local log-level value; generated docs explain age recipient,
private key and provider setup before real secret use. Do not dump environment
values. Docker uses a multistage nonroot API image plus Postgres 18.6, loopback
published ports, healthchecks and local-only example credentials. Inside its
container the API binds 0.0.0.0 while auth stays deny-all. Review/pin image digests
for deployment. The container runtime has **not** been verified here: Docker's
daemon is unavailable; Compose structure can be checked without it.

PG/pgx is real optional connectivity: a configured DATABASE_URL opens/pings a pool
at startup. The SQL migration/query/sqlc config are a **foundation only** (schema
metadata probe), with no app-specific persistence, migration runner, ORM, generic
DB interface or durable audit. `sqlc generate` uses v2 config and pgx/v5; its output
compiles. No PostgreSQL integration pass is claimed without a running database.

Repository checks:

```sh
./scripts/fmt.sh
./scripts/check.sh
go test -race ./...
go test ./internal/project -run '^$' -fuzz '^FuzzEndpointValidation$' \
  -fuzztime=3s -parallel=2
python3 scripts/mutation-smoke.py
```

The scripts accept installed pinned golangci-lint, or mise (review/trust config
first). Tests execute Cobra commands, init both tenancy modes, add same/different
groups, compile/test/vet generated apps, and inject independent policy tests. With
the pinned linter on PATH they additionally run generated fmt twice, prove
idempotence/nonmutating vet and run the full generated checks. Otherwise that
subtest reports SKIP; `pluto vet` itself never silently skips a missing tool.
Safety tests cover conflicts, dry runs, symlinks, unknown manifest fields, metadata
tampering, nested/existing Git, custom hooksPath, staged/ignored changes and hook
failure propagation. Temporary Git fixture commits exist only inside tests.
Mutation smoke reports killed/survived/invalid/timed-out separately and requires all
seeded guards to be killed. No CRAP metrics or comprehensive mutation claim.

[Cobra releases](https://github.com/spf13/cobra/releases),
[TOML strict decoding](https://github.com/pelletier/go-toml),
[mise configuration](https://mise.jdx.dev/configuration.html),

Cobra/TOML dependencies never enter the generated app runtime.

Per-endpoint `internal/app/<group>_<action>.go` bindings are authored constructor
choices. Change the operation constructor and this binding together when adding
repositories. Add typed fields to app.Dependencies and construct/inject them in
app.New. Generated group registries accept narrow Operations interfaces and never
choose concrete implementations; additions preserve authored constructor wiring.

## Session-enabled scaffolds

New projects use manifest schema 6 and published Pluto Auth modules. Authenticated
routes verify sessions, then resolve trusted memberships through the authored
access.Memberships adapter (deny by default). Cookie/Origin protection, optional
opaque bearer credentials, session metadata/logout endpoints, explicit Postgres
migrations and local memory storage are included. No default users or login
provider are created. See the generated README for credential-provider wiring.

Schema 2 projects require manual migration of authored authentication/config/main
files, module pins, paths and migrations before changing their manifest version.
The CLI rejects old schemas without rewriting user code.

## Shared pagination and idempotency

New scaffolds import published `pluto-core` and its separate PostgreSQL adapter;
reusable parsing/cursor/claim/replay code is not copied into applications.
`GET List` explicitly saves `collection = true`; `--collection` opts other names
in, and `--collection=false` opts out. Other GETs remain details. Collections
receive `pagination.Request` through their input and return a shared typed page.
Thin handlers parse/encode it; implement repositories with verified visibility
predicates, immutable deterministic order, a unique tie-breaker and SQL
`LIMIT input.Page.FetchLimit()`. Use `pagination.Finish` after the bounded query.
Default 25/max 100, opaque unsigned scope/filter-bound cursors, no COUNT query.
Cursor boundaries never authorize access. OpenAPI records parameters and metadata.

Authenticated business POST/PUT/PATCH/DELETE routes default to
`idempotency = "auto"` (required); `--idempotency=exempt` is the explicit override
for streaming/sensitive/unsupported routes. Public writes and session lifecycle
are exempt; public idempotency needs an authored verified application scope, never
an anonymous shared cache. Clients supply a 1–128 byte Idempotency-Key per action.
Auth, trusted membership, RBAC and feature gates precede every replay. The default
wiring uses the published Postgres store plus explicit 003_idempotency migration;
without DATABASE_URL business writes return 503 until a durable adapter is wired.
There is no implicit production memory fallback. Tests inject bounded memory.

Completed results retain 24h; pending/uncertain requests block without automatic
lease stealing or retries. JSON capture does not guarantee exactly-once effects:
complete in the same pgx transaction as business/audit writes when required. See
[core guarantees and transaction API](https://github.com/plutoframework/pluto-core).
Only Content-Type and bounded JSON bytes/status are recorded, never Set-Cookie or
arbitrary security headers. Token/credential responses must remain exempt.

Schema 3 migration is manual: update published module pins/go.sum, add the
reference 003 migration, endpoint Collection/Idempotent fields, shared-runtime
transport adapters, Registrar/authentication/main wiring, and eligible endpoint
metadata. Convert authored collection inputs/results/handlers to the shared page
contracts and use bounded repository queries. Copy the new thin adapters from a
fresh scaffold and review them; do not replace authored business logic. Only then
set schema_version=6 and regenerate CLI-owned files. Older manifests are rejected
before writes; regeneration never edits authored models/handlers/operations.

## Optional local credentials

`pluto init --local-credentials` saves `capabilities.local_credentials=true`.
The default remains session-only external credential integration with no public
login/bootstrap route. Local apps import the published password lifecycle and
mount seven POST routes: /auth/enroll, /verification, /verify, /signin, /recovery,
/reset and /logout. GET/DELETE /auth/session remain tenant-free metadata/revocation.
The entire /auth namespace is reserved so generated business writes cannot shadow
credential routes or accidentally cache their sensitive responses.

The local starter compiles but deliberately refuses startup until DATABASE_URL and
app-owned delivery, shared AttemptLimiter and trustworthy HTTP Ingress are supplied
in authored cmd/api/credentials.go. Constructors reject missing dependencies.
Production never silently uses a recorder, no-op sender, in-memory credential store,
hardcoded password or automatic role grant. The member resolver still denies until
trusted app provisioning is implemented; enrollment never grants business access.
The generated README describes Origin, bounded JSON, cookie and opaque response
contracts, post-commit delivery/resend behavior and operational responsibilities.

Apply explicit 004_local_credentials.sql after 001/002/003; no startup DDL. Local
issuance/rotation MUST use password.Service.Sessions() with the SAME NewLocal store.
The library owns hashing, challenges, password reset/disable fencing and sessions;
templates only wire its adapters. Auth root is stdlib-only, password uses x/crypto,
and the optional published pgx adapter currently imports password transitively in
its package even for session-only consumers. The CLI's own dependencies stay small.

Schema 5 and earlier manifests are rejected before writes. Compare a fresh schema-6
scaffold, review published module pins and authored auth/config/main/path/transport
changes, explicitly choose local_credentials=false (external sessions) or true,
apply 004 only for local credentials, then set schema_version=6. Preserve existing
models/handlers/operations; add/check never migrates or overwrites authored code.
An existing session-only app can retain its original schema and binary until it
chooses a manual migration. No implicit generation upgrade is provided.

`mise exec golangci-lint@2.15.0 -- ./scripts/postgres-check.sh` runs disposable real
PostgreSQL HTTP lifecycle tests in generated single/multi apps, then removes the
container/schemas. Without PLUTO_CLI_TEST_DATABASE_URL the persisted test reports
SKIP. It covers missing dependencies, unverified/unknown membership, explicit trusted
binding, Origin, challenge supersession/replay, delivery failure/resend, secure
cookie/no-cache, reset/disable revocation, protected routes and logout. Existing
single/multi generator tests retain pagination, idempotency, RBAC/flags and session
compatibility checks. No messages leave test-process memory.

## Jobs and transactional outbox (schema 6)

Every new app imports published Pluto Jobs v0.1.1 and its Postgres adapter v0.1.0.
It includes explicit migration `005_jobs.sql`, `cmd/worker`, an authored worker
composition file and a CLI-owned registration catalog. No broker, startup DDL,
provider client, implicit worker goroutine or copied worker implementation.

```sh
pluto add job invoices Send --kind invoice.send
pluto fmt
pluto vet
go run ./cmd/worker
```

The command adds an authored typed payload/request constructor, handler and unit/
fuzz tests in `internal/jobs/invoices`, then updates only the managed registry
and TOML. Existing handlers remain intact. Duplicate kinds/identifiers, traversal,
modified registries and file collisions fail before writes; `--dry-run` previews.
Authored constructor bindings in `internal/background/<group>_<action>.go` receive
typed Dependencies; extend them to inject adapters without globals or generated
registry edits. Handlers deliberately return an unimplemented error until authored: they never
acknowledge fake success. With no registrations, the worker refuses to claim work.

Use the typed request with the published store's `EnqueueTx(ctx, tx, request)`
inside the **same pgx transaction** as the domain write and audit. App repositories
own commit/rollback; do not use independent Enqueue for transactional writes.
Operations continue to depend on consumer-sized repository interfaces, not pgx.
Set TenantID from the verified operation scope, then validate resource ownership
again when loading canonical records for delivery. Never enqueue passwords, raw
auth challenges or cookies. Auth delivery remains synchronous and separate.

Worker settings live in nested `config.Config.Jobs`, initialized from the library's
bounded defaults. Run it as its own process with DATABASE_URL. The Docker image
contains both API/worker binaries; `docker compose --profile worker up --build`
starts the opt-in worker after handlers have been implemented. `mise run worker`
is also scaffolded. Migrations mount for fresh Compose databases only.

Delivery is at least once. Handlers must honor cancellation, use a stable effect
key such as job.ID, and tolerate acknowledgement loss. No heartbeat, external
sender or production monitoring/retention policy is provided. Operators inspect
fixed diagnostics and reconcile uncertain outcomes; never log job payloads.

Migrating schema 5: compare a fresh schema-6 project, add the published pins/sums,
005 migration, worker/config/background files and empty managed job registry.
Preserve authored application logic; only then set schema_version=6. For earlier
schemas, also complete the credential/Core migrations described above. Add/check
never upgrades authored files automatically. PostgreSQL generator integration
covers commit visibility, rollback and bounded retry/failure without fake success
for both single- and multi-tenant apps.

The mise sqlc pin uses the explicit Go backend instead of an unavailable registry
alias. sqlc 1.31.1 needs Go 1.26+ for generation; Go can fetch that toolchain without
changing the application's Go 1.25.5+ target or runtime dependency graph.
